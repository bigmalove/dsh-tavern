# 插件生态：吸收一个人永远想不到的巧思

## 问题：不缺实现，缺信息

有了 AI，实现已经不是瓶颈。只要知道一个功能该做什么、做成什么样，哪怕没有现成代码，也能很快复刻一份。

真正的瓶颈是**知道该做什么**。玩家怎么玩、卡作者怎么写卡、哪里真的卡手、哪种做法更省事，这些信息分散在成百上千个人手里，而且常常只在他们动手的那一刻才浮现。维护者一个人的经验、试玩和想象，覆盖不了这些。凭空设计功能，只是在用有限的信息猜。

## 办法：像市场一样，让分散的信息自己冒出来

市场之所以有效，不是因为有人掌握了全部信息，而是价格把分散在每个人手里的信息汇总了起来：没有谁需要知道一切，信号自己会出现。

这里的关键不在于谁知道得多。单个插件作者掌握的信息，往往远不如维护者全面；但每个人站的位置不同，恰好能照到维护者的盲区。把很多人各自的一小块拼起来，覆盖的范围是任何一个人都达不到的。

插件生态起的是同样的作用。Tavern 开放接口，用户按自己的需要写插件；每个插件都是一个**被做出来的巧思**，是只有那个作者才想得到的信息。好不好用，装上就知道，这就是信号。

两个原因让「做出来」比「说出来」更有用：

- **描述会丢信息，能用的东西不会。** 一段需求，维护者可能判断「没必要」；同一个想法做成插件摆在眼前，一试就知道好不好。
- **成本由最有动力的人承担。** 想要这个功能的人最清楚它该是什么样，也最愿意花时间把它做对。

## 吸收：两种方式

**吸收成品。** 插件本身就好，精简后做进本体。

> 人物卡宫格：最初作为需求被婉拒（「自定义界面布局，不内置」）。作者用开放的接口做成插件，试用后效果很好，于是精简为内置的「宫格」视图：去掉列数设置、多余的信息行和窗口放大，只留下「两三百张卡时按封面找卡更快」这个核心发现。（[#218](https://github.com/flizzywine/dsh-tavern/discussions/218)）

**吸收思路。** 插件本身不适合内置，但它的做法揭示了维护者不知道的事。

> 人物卡转 MVU：有插件用程序把人物卡转成 MVU 版，不耗 token。插件没有内置，但「这一步能用程序做，不必交给模型」这个关键点，启发了内置「转成 MVU 版」的改进，大幅降低了 token 消耗。没有这个插件，这个做法不会被想到。

所以看一个插件，不只问「要不要内置它」，更要问「它知道什么我们不知道的」。很多插件不值得内置，但值得读一遍代码。

## 让这件事持续发生

信息只会从开放的地方流进来，作者也只会在被善待时继续做插件。

- **接口尽量开。** 接口开到哪里，就能从哪里收到巧思；没开接口的地方，好主意做不出来，也就看不见。拿不准值不值得做的需求，优先开接口让需要的人做出来，而不是自己猜着做。接口要简单、稳定、只加不改，见[插件开放层设计](plugin-design.md)和[插件接口](plugin-api.md)。
- **吸收时善待作者。** 在提交中用 `Co-authored-by` 署名原作者，公开说明吸收了什么；插件用的接口保持不变，原插件照常可用。
- **吸收的是信息，不是代码。** 本体按自己的简洁程度取舍：少设置、少开关，只留下真正的发现。本体不因吸收而变胖。
- **不是什么都吸收。** 多数插件就该一直是插件，各取所需。吸收的门槛是：对大多数玩家有用，并且能以很低的维护成本放进本体。

## 和项目范围的关系

[项目范围](scope.md)的「不做」清单拒绝的是**照需求内置**，不拒绝信息。清单外的想法，欢迎做成插件；做得好的，会以上面的方式进入本体。
