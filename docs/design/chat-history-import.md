# SillyTavern 聊天记录导入

状态：已在 `feat/chat-history-import` 实现并完成下述验证。导入沿用原生 Session、40 个时间线恢复点、末轮重新生成、分叉和后台协调机制。2026-09-07。

## 目标与范围

用户先选择人物卡，再导入 SillyTavern 单人聊天 JSONL，创建独立的 DSH 会话。打开后能查看原有消息，并从最后一条继续输入。导入过程不调用模型。

恢复正文历史，并恢复文件中可识别、与目标人物卡兼容的 MVU 快照，使用当前人物卡、关联世界书和当前预设。它不等于恢复原环境：缺失的 MVU 状态、插件数据库、后台执行、世界书触发记录及剧本进度不从正文推测。导入文件中的提示词、脚本和扩展字段是数据，不作为导入器的执行指令。

## 用户流程

唯一入口放在选好人物卡后的“游戏准备”页底部：“导入聊天记录”为次要按钮，“开始游戏”为主要按钮。不放到已有对话的操作菜单，避免被理解成追加到当前对话。

1. 点击“导入聊天记录”，打开文件选择器，接受 `.jsonl`；取消后保持原页面。
2. 解析成功后，在当前弹窗用导入预览替换开场白预览。展示目标人物卡、文件名、有效消息数量、最后一条消息摘要，以及必要的兼容说明。
3. 底部显示“返回”和“导入并打开”。返回恢复游戏准备页，保留人物卡选择。导入不要求选择开场白。
4. 点击后锁定提交并显示进度。成功后打开新对话，定位到最后一条消息，不自动生成下一段。
5. 解析失败原位显示行号、原因和“重新选择文件”；提交失败保留预览，允许恢复同一次导入。

预览文案：

```text
导入到：某某人物卡
文件：聊天记录.jsonl
共 35 条消息

最后一条消息：
……摘要……

将创建独立对话，使用这张人物卡及其关联世界书。

[返回]                         [导入并打开]
```

预览按检测结果区分“将恢复 MVU 状态”“未找到可恢复的 MVU 状态”“状态格式暂不支持／与人物卡不匹配”，仅在校验通过后承诺恢复。插件专用数据另列兼容说明。预览正文按文本显示。状态缺失按最近有效快照或人物卡初值降级，并明确提示；结构不兼容时允许换卡或明确选择“仅导入正文”。

## 解析契约

新增独立纯解析模块，输出规范化消息、预览和诊断；解析阶段不创建 Session。服务端在提交前重新验证内容、目标卡和文件大小。大小及消息数量上限由实现选定并写入测试，超限明确报错，不能静默截断。

| 输入 | 处理 |
| --- | --- |
| 首行 `chat_metadata/user_name/character_name` | 识别头部；人物卡绑定以用户选择为准。名字可能为 `unused` |
| `is_user`、`mes`、`name`、`send_date` | 保留顺序、正文、说话者、原时间；缺少必需字段或类型错误报具体行号 |
| `is_system` | 作为 ST 特殊消息标记识别，不能直接映射成模型 system 角色。第一版排除并在预览说明数量 |
| `extra.type` 的旁白及工具消息 | 需要显式识别；第一版不支持的类型报兼容错误，不能当普通助手正文悄悄导入 |
| `swipes/swipe_id` | 当前正文以 `mes` 为准，读取原选中索引对应快照后归一为 DSH 槽位 0；其余候选正文及变量直接丢弃，不归档、不提供切换入口 |
| `extra.reasoning`、签名、模型调用数据 | 不进入正文及新模型请求 |
| `variables[swipe_id]` | 提取当前回复对应的 MVU 快照，保留消息关联；缺失索引、空值及格式错误显式诊断，不能取其他候选的状态替代 |
| `initialized_lorebooks`、`schema` | 随快照保留并校验语义；不能仅凭字段存在认定可用，不执行来源中的代码 |
| 头部 `chat_metadata.variables`、插件数据、未知扩展 | 第一版不恢复，直接丢弃；不作为历史原文件另行归档 |
| BOM、CRLF、尾部空行 | 正常处理；正文内容不二次做宏替换、正则加工或添加前缀 |

仅有头部或过滤后无可用消息时拒绝导入。允许助手开场、连续同角色消息和以用户消息结尾；不能用数组奇偶位置猜角色。连续同角色正文以空行连接，保留来源行号，取合并末尾状态，预览明确提示；由此保持原生一组输入和正文的结构。末尾用户消息作为尚未获得回复的输入保留，分叉等操作遵循原生限制。第一版拒绝群聊及附件依赖型消息，并说明原因。文件上限 8 MB、2000 条源消息。

玩家称呼可从有效用户消息建议，预览允许修正；不以头部名字自动覆盖。对话标题默认使用去掉扩展名的文件名，可继续使用现有重命名功能。

## 新 Session 的构造

推荐分成解析器、导入协调器、原生事件适配器，RPC 名称在实施时按现有约定确定。

1. 预览完成后，提交目标卡、文件内容或受控暂存引用、玩家称呼，以及本次操作 ID。
2. 取消普通游戏预热，创建专用新 Session。复用稳定上下文初始化，显式跳过普通开场及开场恢复逻辑。
3. 固定规则先写入，历史按原顺序追加。导入专用种子如有需要，只写一次，不能带“从人物卡开场开始”的指令。正常新游戏行为保持不变。
4. 将用户正文和助手正文映射为宿主接受的原生事件，按玩家逐轮游玩的结构建立消息、DSH turn、故事轮次、commit 和 checkpoint 的关联。每条消息记录来源行号、操作 ID、原时间；宿主事件时间表示导入时间。逐轮构造恢复点，并按原生规则仅保留最近 40 个；不能把整段历史当作一个轮次。
5. 保存每条消息对应的 MVU 快照及来源映射，将经校验的末尾有效快照接入当前权威状态，再通过原生 Surface 和 UI 投影显示历史及状态栏。不能只写 `chat.messages` 或 `.tavern/` 文件。
6. 持久化并验证可重新加载后，登记为可见会话，返回 Session ID，前端打开。

每个有助手回复的历史玩家输入，都必须通过共用正文 Context Planner、ForegroundFrame Builder 和 Session Adapter 构造原生 Frame，持久化顺序为玩家输入、Frame 上下文、助手正文。包括完整的“小说续写引擎”任务指令、当前人物卡任务要求、适用的 MVU 后台规则及预设中段指令；不在导入模块另抄提示词。第一条纯助手开场和尚无回复的末尾用户输入不伪造已执行的 Frame。动态世界书按导入时绑定的人物卡与世界书、逐轮已有正文及变量快照，通过原生召回与模板投影构造；这是 DSH 上下文重建，不声称恢复了酒馆当时的请求。缺失的剧本位置和现场描述不回填为当时已存在的贡献。

事件适配实施前要用宿主契约验证：是否需要 turn/step 外壳、Agent 下一轮计数如何恢复、连续角色与末尾 user 如何封闭历史。宿主要求的外壳必须标记导入来源，不虚构真实模型调用、工具结果或后台成功记录。仅仿照开场的事件形状不足以证明可续聊。

## 状态与恢复边界

### MVU 快照恢复

已核对用户提供的 MVU 样本（2026-09-07 导出）：1 行头部、3 条消息。每条消息的 `variables` 数组均包含 `stat_data`、`initialized_lorebooks` 和 `schema`。首条消息有 7 个候选，`swipe_id = 1`，当前状态对应 `variables[1]`；其余两条对应 `variables[0]`。`stat_data` 包含世界时间、日期、场景和人物状态。个人样本正文不复制到文档或测试夹具。

该样本三条消息选中的 `stat_data` 完全一致：已证明文件包含结构化快照，尚未证明发生变量变化后的恢复正确性。`schema` 字段存在也不代表它是完整可执行模式，实施时需验证实际格式。

恢复契约：

- 正文与快照按同一条消息、同一个候选编号配对。没有 `swipe_id` 的普通用户消息按已验证的格式规则取槽位 0；非法索引不能静默回退。
- 保留每条有效消息的选中快照与来源行号、原选中索引；未选候选正文和变量直接丢弃。持久化记录仅包含归一后的选中内容，临时上传文件或暂存内容不作为原始文件长期归档。
- 逐条处理快照：缺失时沿用此前最近有效快照，并标记该轮为继承状态、提示状态可能滞后；尚无有效快照时使用人物卡初值并明确提示。整份文件没有快照时同样处理，不调用模型补算。末尾状态由此顺序推导，不能将继承值宣称为该轮已结算结果。
- 通过现有权威状态写入及投影链路恢复状态栏，并让下一轮 MVU 更新从该快照继续。仅让页面显示一段旧状态栏 HTML 不算恢复。
- 初始化顺序应保证人物卡初值、世界书初始化和重启恢复不会覆盖导入快照；快照恢复不重跑历史结算，不虚构后台执行成功记录。
- 导入完成处建立状态基线，记录来源快照和恢复结果。正文内状态栏、消息 MVU 数据、聊天级变量及其他插件数据库分别识别。
- 校验目标卡所需状态结构与快照是否兼容，不仅凭人物卡名字不同阻止导入。实际结构不兼容时保留预览，让用户换卡，或明确选择“仅导入正文”；后者使用人物卡初值并提示，不静默丢弃变量。具体校验能力和 DSH 写入接口待运行验证，暂不承诺任意 MVU 卡完整恢复。

第一版从人物卡 `<initvar>` 或关联世界书 `[initvar]` 读取静态 YAML/JSON 初值，以初值的键和类型检查快照。动态模板初值暂不执行；若缺失快照或仅导入正文需要该初值，会明确报错。`schema` 和 `initialized_lorebooks` 随选中快照保留，最终由现有 MVU 运行时读取；状态栏仍由人物卡自己的脚本和正则渲染。

导入及历史恢复点使用原生 `settleStatus: done` 表示当前数据无待结算工作，后台 participant 使用原生 `needs-session`。不在后台协调器添加“导入会话”分支，也不追加自定义宿主事件；导入来源只放在消息元数据，失败重试核对原生事件前缀。

### 已确认的 DSH 接入路径（源码级）

- `tavern-helper-context.js`：原生消息使用 `swipeId` 和 `variables[swipeId]`。导入的 `swipe_id` 需要映射；`replaceTavernHelperVariables` 已提供按消息及槽位写入的逻辑。
- 同模块 `projectTavernHelperContext`：将当前槽位投影为状态栏脚本可读的 `variables`，并提供 `swipes_data`、`turnMessageIds`。导入消息及轮次必须进入这条既有投影链路。
- 同模块 `lastTavernHelperVariables`：倒序读取选中快照，但只检查是否为 `undefined`，空对象也会返回。导入器要另行验证 MVU 快照有效性，不能依赖此函数处理状态缺失。
- `turn-orchestration.js`：下一轮继承最近变量到用户及助手消息，助手消息标记 `mvu.pending` 后由后台继续更新。导入历史保留快照，但不设为待结算。
- `tavern-script-host-adapter.js`：变量写入经 `updateVariables`、`writeChat` 持久化；现有 MVU 结算通过独立草稿及 effect 提交。导入应接入现有存储和时间线机制，不调用历史结算来制造状态。
- `index.js` 的 `writeChat`：持久化 Chat 后同步摘要并发布协调更新；`src/client/main.js` 的 Helper Context 更新逻辑检测变量变化并发出 `mag_variable_update_ended`，供状态栏刷新。

这些源码证明接入位置存在，尚未构成运行验证。必须实测初始化不覆盖快照、刷新与重启后状态保持、下一轮继承和更新正确。

### 已确认的历史操作语义

用户要求导入后像玩家逐轮玩过的原生 DSH Tavern 对话：构造玩家输入、助手输出及其原生轮次结构；可以在最近 40 个回退点内逐轮回退，与原生会话保持一致；重新生成只作用于当前有效历史的最后一轮。

- 导入历史与导入后的新消息共用最近 40 个回退点的上限，不设置“只能退到导入完成处”的限制；更早正文保留可读，但超出上限后不提供回退。
- 每轮建立原生时间线恢复点，关联该轮消息范围、Surface 投影、变量快照和后续续玩所需状态。先核对原生 checkpoint 契约，再构造导入 checkpoint；不能仅伪造一个完成标记。
- 回退后显示及模型上下文都恢复到目标轮次，MVU 恢复该轮对应快照，下一次输入从该位置继续。
- 重新生成只对当前最后一个可重新生成的助手轮次开放。要重做更早一轮，先回退使其成为最后一轮，再使用正常重新生成机制。
- 原生 Session 事件仍 append-only；回退和重新生成复用项目既有投影及时间线机制，不删除原始导入事件。
- 来源标记表示历史由导入构造；产品行为等同原生轮次，不捏造实际模型调用、计费或后台工具执行。
- 有完整 MVU 快照的轮次据实恢复；缺失轮次按前文继承规则构造 checkpoint，并保留状态来源及降级标记。回退可用，但不能把继承值或初值冒充该轮实际历史状态。
- 导入后即为原生 DSH 对话，支持现有从当前进度分叉。要从较早进度分叉，先回退到该处。子会话复制当前有效正文与变量，按现有机制建立独立时间线、清空父会话恢复点和后台边界；保留宿主事件对应的回退及重新生成投影。父会话不受影响。

### 已确认的后台 Agent 起点

导入完成后，后台 Agent 以当前最新轮次及对应状态为起点，与前台有效历史对齐。导入历史不重复结算，打开会话或恢复服务也不触发历史补结算；首次正常后台结算由导入后的新一轮触发。

- 初始化后台时绑定新 Session、当前分支、最新轮次及状态 revision，读取经恢复的 MVU 快照。不能沿用其他会话的后台上下文、待处理任务或提交回执。
- 导入轮次不设置待结算标记，不制造历史任务队列；后台就绪不等于立即运行一次结算。
- 新轮次的结算输入承接导入状态，按正常前后台协议处理。后台需要的规则和历史上下文可读取，但读取历史不等于重放历史任务。
- 回退或重新生成后，后台有效上下文及任务归属要与前台当前位置同步，旧位置的迟到结果不得提交到新位置；保持既有 append-only 和稳定提示词前缀约束。

### 后台回退复用现有机制

采用同一套时间线及后台生命周期机制，不新增导入专用回退系统，也不在每次回退时一律重建后台。

| 目标位置 | 处理 |
| --- | --- |
| 导入后真实游玩的轮次，存在可恢复后台边界 | 复用现有 Session、boundary 和 rewindTo 恢复有效上下文 |
| 导入历史中的轮次，没有后台执行边界 | 走 needs-session 分支，从目标轮次及变量快照建立新后台起点，不重放历史结算 |

源码依据：`story-timeline.js` 已管理后台 participant 的 Session、boundary、rewindTo，以及缺少恢复来源时的 needs-session 状态；`background-agent-task.js` 的 rewindSurface 在任务执行前应用后台边界。后台本身有 Session 历史，导入轮次缺少的是对应的后台执行历史。导入 checkpoint 应如实记录这一缺失，不能复制其他轮次的后台边界。

`round-history.js` 的重新生成已有生命周期版本推进及相关结算取消逻辑，应复用该路径。提交端仍要验证当前分支、轮次、revision 和生命周期，不能仅依赖取消任务来防止迟到结果写入。

接入风险：`background-agent-sessions.js` 的 Session 选择会在未指定 ID 时回落到 `residentSessionByParent` 缓存。因此仅清空时间线中的后台 Session ID 不足以保证新建。实施时必须让 needs-session 的意图明确传到运行器，正确失效或绕过旧常驻映射，防止复用已失效上下文；不要在普通可回退分支无条件清空缓存。

上述是源码级设计依据。运行验收需覆盖“真实轮次回退 → 进入导入历史 → 从该处续玩”，以及新起点创建后刷新、重启、旧任务迟到的情况。

### 已确认的剧本处理

导入沿用人物卡的正常模式选择：绑定剧本则按剧本模式继续，未绑定则按自由故事模式继续。导入功能负责恢复会话历史及可用状态，不负责判断历史是否符合剧本，也不因剧情偏离而阻止导入或改为自由故事模式。

外部记录没有 DSH 剧本进度时，使用现有剧本模式的正常初始化及后续推进机制；不根据正文推测游标，不新增手动定位步骤。剧情衔接、偏离和推进策略由剧本模式负责，导入不修改人物卡绑定。

### 已确认的降级与候选处理

快照缺失按最近有效状态或人物卡初值处理并提示；实际结构不兼容由用户选择换卡或仅导入正文。未选候选正文及变量直接丢弃。导入历史支持原生分叉，不设置额外禁用条件。

使用持久化的 `pending → writing → ready/failed` 或等价操作状态。消息 ID 由操作 ID 与源行号稳定派生；重复提交或断线重试返回同一结果。显式重新导入允许创建另一会话。

半成品不出现在正常会话列表；恢复流程按已追加事件续写，不删除或改写原生历史。`recover/ensureOpening` 必须识别导入来源，重启后也不会补开场。打开失败提示重试打开已创建会话，不能再创建一次。跨存储写入不是天然事务，需要以 ready 标记和恢复流程保证一致性。

## 实施顺序与验收

1. 解析器：用无敏感内容的合成 JSONL 覆盖头部、角色、swipes、特殊消息、损坏行和末尾 user。个人聊天文件不加入仓库夹具。
2. 原生导入：先完成稳定前缀、事件映射、持久化、重启恢复、幂等与失败注入测试；验证下一轮计数不冲突。
3. MVU 与轮次恢复：接通消息快照、当前权威状态、状态栏和每轮 checkpoint；验证初始化不覆盖快照、后台不重放历史、逐轮回退及最后一轮重新生成。
4. UI：入口、文件选择、预览、错误恢复、进度、成功打开；取消预热与普通开场恢复交叉路径必须覆盖。
5. 构建客户端生成产物，重启实际 Tavern，验证桌面及窄屏流程。

完成标准：

- 人物卡未选定时不能提交导入；新会话绑定选择的卡及其当前上下文。
- 绑定剧本的卡导入后保持剧本模式，未绑定的保持自由故事模式；不因历史与剧本不一致而阻止导入，不增加进度定位步骤。
- 导入不发生模型调用，原会话保持不变，开场不重复。
- 导入、打开、刷新及服务重启均不派发历史后台结算；新一轮才触发正常结算，输入状态与导入后的最新轮次一致。
- 回退或重新生成期间，旧后台任务的迟到结果不能覆盖当前状态；下一次后台任务与当前前台分支、轮次及 revision 对齐。
- UI 消息顺序与规范化输入一致；刷新和服务重启后结果一致。
- 用受控模型端点捕获导入后第一次真实 provider 请求：稳定规则在前，历史顺序正确，只有选中的回复，无思考字段及多余开场，最新输入仅出现一次。仅检查 UI 或中间 `model-requests` 不算通过。
- 使用具有明确变量变化、多个候选且选中非零索引的合成夹具，验证正文与快照配对、当前状态、刷新及重启保持一致。
- 实际状态栏读取导入值；下一轮后台更新从导入值继续，前台请求中的当前状态投影与之相符。
- 覆盖快照缺失、空槽、非法索引、格式不兼容以及最新快照落后于最后消息的诊断，避免把初始化值当成同步成功。
- 连续回退跨过多个导入轮次，验证每一步的 UI、实际 provider 请求历史及 MVU 快照都对应目标位置；刷新、重启后仍可继续回退和续玩。
- 当前最后一轮可重新生成，更早轮次不直接提供该操作；回退后目标轮成为最后一轮时可重新生成。旧正文从有效模型上下文移除，原始事件保留。
- 导入完成后的新轮次可正常生成、后台结算，并可在最近 40 个恢复点范围内回退进入导入历史。
- 从导入历史和导入后的轮次分别分叉，验证子会话正文、变量、后台起点及续玩正确，父会话保持不变。
- 未选候选正文及变量不会出现在持久化导入资料、可见历史或模型请求中；原选中索引非零时归一后正文与变量仍配对正确。
- 快照缺失的继承值及来源提示正确；结构不兼容时换卡和明确选择仅导入正文两条路径均可用。
- 双击、断线、部分写入和打开失败均不会产生重复历史或重复可见会话。

本文不表示宿主事件兼容性和 MVU 续聊已验证；这些是实施阶段的验收任务。

### 极端超长导入的首次容量准备

仅对尚未续玩的导入会话，在第一次正文请求取得实际模型后检查容量。能放进模型可用窗口的历史保持完整；超出窗口时，不调用摘要模型，以原生 Surface replace 将中间旧轮次移出有效上下文。保留固定开头、开场、本轮输入与 Frame、最新状态以及尽可能多的最近完整轮次；没有独立开场时保留首个完整轮次。完整轮次包含玩家输入、Frame 和助手正文，不能从中间截断。

裁剪目标不超过当前模型上下文窗口的 80%，同时扣除输出额度及安全余量。采用宿主 token 估算并为非 ASCII 正文增加保守估算下限，因此这是容量估算而非供应商 tokenizer 的精确保证。模型容量未知、必留内容或最近一轮本身过大时明确报错，不能靠无限重复压缩尝试解决。

原生事件保留全部原文，Chat 正文保持不变，history_recall 可检索和按轮读取被裁剪的历史。回退则属于剧情撤销：从当前 Chat 历史移除的轮次不再参与召回，原始事件仍遵守追加式存储。若回退目标已经不在有效 Surface，拒绝操作并说明原因，避免误撤销其他轮次；该边界不增加恢复点数量，仍保持原生最近 40 个恢复点。

准备结果先随原生 Session 事件落盘，再记录到导入元数据；失败重试复用已有标记。首次已组装的请求同步移除对应消息，后续请求及原生压缩读取整理后的 Surface。完成准备后继续使用原生压缩机制，不建立永久的导入裁剪分支。导入后不必先续玩，可以立刻手动压缩：超出窗口的历史由分段压缩逐段总结，摘要请求不会超窗；压缩后的首次续玩仍做容量检查，此时通常已无需裁剪。

验证覆盖不同模型容量、完整轮次保留、持久化与失败重试、裁剪历史召回、撤回正文不再召回，以及实际安装的原生压缩引擎：准备后不触发压力压缩，后续正文增长后正常触发一次原生摘要。此项使用受控模型适配器，不代表在线供应商 HTTP 验证。
